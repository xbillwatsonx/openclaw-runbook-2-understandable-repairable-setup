# Prompt: Practice One Safe Change End to End

Copy this prompt into your OpenClaw chat.

---

**Runbook bridge:** Read the released runbook at <https://raw.githubusercontent.com/xbillwatsonx/openclaw-runbook-2-understandable-repairable-setup/v0.1.1/runbook/oc-runbook-2-understandable-repairable-setup.md> before acting. Relevant section: **§5, Plugins: install, remove, verify** and **§8, The safe-change workflow**. This prompt helps the reader complete one controlled plugin lifecycle; the agent should inspect first, pause at approval gates, change only the selected plugin, verify each state, roll back on failure, redact secrets, and record the outcome.

I want to practice one full plugin lifecycle with a trusted plugin spec that I select: install → verify → inspect → uninstall → verify. Follow the complete workflow: Back up → Change one thing → Validate → Test → Record. Do not choose, recommend, or invent a plugin ID for me, and do not make any destructive or hard-to-reverse change.

Please guide me through this workflow:

1. **Select and inspect; do not install.** Ask me for the trusted plugin spec I selected. If I have not selected one, explain that I can discover candidates with the read-only `openclaw plugins search <query>` command, browse ClawHub, or use a local plugin path I already trust; do not choose one for me. Confirm that my installed OpenClaw CLI recognizes the selected source type. Review available provenance, requested capabilities, install-policy warnings, version/pinning choice, expected installed plugin ID, and the uninstall command. If any of those are unclear, stop.
2. **Back up.** Confirm that `~/Backups` exists; if it does not, pause and ask before creating it. Run `openclaw backup create --verify --output ~/Backups` and confirm the archive is valid. Record the pre-change output of `openclaw plugins list` and `openclaw plugins doctor`. If the backup or pre-check fails, stop.
3. **Approval gate: install.** Show me the exact `openclaw plugins install <trusted-user-selected-spec>` command and explain every flag. Explain whether this command will run from a separate shell or through the running Gateway: OpenClaw reports that a running-Gateway install can request an automatic restart when config reload is enabled, while a separate-shell install requires a later manual restart; config reload can also restart connected channels. If the no-restart boundary cannot be preserved, stop and ask for separate service-impact approval. Do not add `--accept-capabilities`, `--acknowledge-install-policy-warning`, or `--force` unless I have reviewed and explicitly accepted what that flag covers. Wait for my explicit approval before running the install command.
4. **Change one thing.** After approval, install only that plugin. Treat installation as executable-code installation: it writes tracked plugin files and records and may add or update plugin configuration. It can register the plugin enabled, or disabled when required configuration is absent. Do not enable, disable, update, restart the gateway, or change anything else. If installation reports failure or an uncertain partial result, stop, preserve the output, and inspect with `plugins list` and `plugins doctor`; do not guess an ID or proceed to uninstall until the exact installed ID and ownership are confirmed.
5. **Validate the installed state.** When the exact installed ID is confirmed, run `openclaw plugins doctor`, `openclaw plugins inspect <installed-plugin-id>`, and `openclaw plugins list`. Confirm the actual ID, source/version, declared capabilities, and enabled/disabled state. If there is a new failure, policy block, unexpected sibling entry, or config change, stop. Use the reviewed uninstall preview only when the exact installed ID and ownership are known; otherwise report the blocker and preserve evidence. Do not invoke the plugin's capabilities.
6. **Understand the runtime boundary.** Record the exact restart/config-reload message printed by the install. A separate-shell install or removal requires a later Gateway restart before the running Gateway reflects the code change. This bounded exercise does not run a restart command or claim runtime verification. If the install reports that an automatic restart was requested, or config reload restarted connected channels, stop and record that the no-restart boundary changed. Any further runtime testing needs separate approval, a service-impact warning, health checks, and a rollback plan.
7. **Preview uninstall.** Run `openclaw plugins uninstall <installed-plugin-id> --dry-run`. Explain the full preview. Depending on the package, uninstall can remove plugin settings, install/index records, allow/deny entries, exact matching load paths, managed files, sibling policy, and related slot/channel references. It leaves an explicit `enabled: false` marker for each removed plugin ID. The dry run shows only effects that apply to the selected installation; if any previewed effect is unexpected, stop.
8. **Approval gate: uninstall.** Show me the exact interactive `openclaw plugins uninstall <installed-plugin-id>` command. Do not use `--force`, which skips confirmation, or `--keep-files`, which leaves installed files, unless I separately request and approve the exact effect. Wait for my explicit approval.
9. **Roll back.** After approval, uninstall only that plugin through the interactive confirmation. If uninstall fails or ownership is ambiguous, stop and report the blocker; do not use `--force` automatically.
10. **Verify rollback.** Run `openclaw plugins list`, `openclaw plugins doctor`, and `openclaw plugins inspect <installed-plugin-id>`. Compare them with the pre-change output and the uninstall preview. Success means the managed package is no longer installed, any remaining `enabled: false` marker matches the documented uninstall behavior, no new plugin health issue exists, and no unrelated state changed. Remember that a running gateway still needs a separately approved restart before its loaded code state can be claimed to match disk.
11. **Record.** Note the date, selected spec, installed ID, approvals, commands run, enabled/disabled result, validation result, uninstall dry-run preview, confirmed uninstall result, before/after comparison, restart-not-performed boundary, and how the verified backup could be used if residual changes remain.

Important:
- Do not run `openclaw reset`, the top-level `openclaw uninstall`, or any unrelated destructive command. The scoped `openclaw plugins uninstall <installed-plugin-id>` is part of this approved exercise.
- Do not change credentials, tokens, or security settings.
- Do not proceed without a user-selected trusted spec, a verified backup, a known plugin ID, a clear uninstall plan, and explicit approval at both state-changing gates.
- Stop if capability requests or policy warnings are unclear or unacceptable, the source cannot be trusted, verification fails, or rollback would affect unrelated files.

After the workflow, summarize what I did, what I learned, the evidence that the managed install was removed cleanly, the fact that no gateway restart or runtime-capability test occurred, and any residual risk. Do not claim completion unless every success condition in step 10 is met.
